# First implementation: supported scheduler contract

**Design question:** What is the smallest source-bound comparison that a reviewer can reproduce from committed Quint models without running the experiment drivers?

This is the first release's semantic contract, not a specification of flags, a review file format, a language, a compiler, or an instrumentation technique. The [comparison contract](comparison-contract.md) defines the general set comparison. This document scopes its first use with original schedulers; the [black-box acceptance cases](first-release-acceptance.md) define the release gate. The existing CLI is a separate, pure-adapter prototype.

## Inputs and snapshot isolation

- Resolve OLD and NEW once to commit IDs in one Git repository. Read each selected entrypoint and its transitive file imports as regular blobs from that commit's tree. Resolve paths relative to the importing source and keep the resolved path inside the snapshot. No checkout, working-tree or index fallback, replacement objects, symlink traversal, submodule traversal, or external source imports. A missing or unreadable required blob or an import that cannot be resolved is `incomplete`, not a missing public action.
- A review pairs one scenario across the commits, with an explicit instance on each side: the entrypoint, Quint module and any constant values, original initialization predicate, and original scheduler action. Keep the set of all original initial states and the native scheduler's guards, updates, and choices. The entrypoint can import or re-export the scheduler from another file. Scenario and observation expressions may be supplied externally; they cannot add or replace model transitions.
- A review selects a finite list of public label histories (support lengths zero through two) and an observation for each side with corresponding meaning and value types. Only the listed histories are results; a prefix is not reported unless selected. Restrict the first release to finite reachable state spaces it can check deterministically. Finiteness or closure must not be assumed from a short public history.

## What can be bound

Each side supplies its own explicit mapping. A binding identifies one **occurrence** of a direct action call in an action position of the selected scheduler and verifies the resolved callee in the selected module instance. Preserve the repository path, module, scheduler, call location, and callee identity as evidence. The same definition may be called twice with identical arguments, guards, and effects; those are still separate sites. Names, branch order, source offsets, and compiler-generated identifiers are not cross-revision keys. A moved call or renamed declaration must be mapped on its own side, not inferred by similarity. Stale, ambiguous, conflicting, or unresolvable bindings are `incomplete`; neither a matching state effect nor a successor event may substitute for a call binding.

The supported scheduler shapes are:

- An action-position `any` (choice), `if` (then/else), or payload-free `match` (arms), including nesting in those positions. Resolve the original conditions and scrutinee; do not treat calls in them as scheduled public calls.
- A direct public call as a leaf, or as the single action call in an `all` leaf with state guards and assignments. The selected call is nullary or has scalar literal arguments (integers, including negative integers, booleans, or strings). Run the whole original branch, not the callee alone. Calls inside the callee and nondeterminism in the callee remain part of that one original step.
- A leaf explicitly designated hidden, for example a guarded assignment with a local finite `nondet` choice, or a native call with its accompanying updates. A hidden branch is an original scheduler step without a public label, not a new step or a shortcut around a guard. Do not bind public calls underneath opaque hidden leaves or local binders. General matching inside helpers, payload-binding matches, several action calls in one leaf, and comparing a public call's locally bound or computed arguments are deferred. Unsupported shapes needed to validate the review are `incomplete`.

A site can carry one unconditional label, or different labels selected by mutually exclusive equality tests of one resolved pre-state scalar variable against distinct literals (e.g., `round == 1` and `round == 2`). These tests classify executions; they are not extra model guards. A call that matches none of its site's label tests, or matches a label out of order, is excluded for that history, never automatically hidden. Hide only explicitly identified branches; unlisted branches are excluded, not inferred to be internal. One site cannot be both hidden and public. The review must deliberately designate a label absent on a side if it has no corresponding scheduled binding there. This is an assertion about the review mapping, not proof that a same-named Quint definition occurs nowhere; a failed selector is never implicit absence.

## Matching and checking histories

Starting from every initial state, follow any number of explicitly hidden original steps before the first public step and between public steps. At each public step accept only the next requested label. Do not skip a public step to look for a later match. A matching execution ends immediately after the last public step; the empty history ends at initialization. Evaluate the selected read-only observation there, not after hidden updates, and keep distinct typed values (at least integers, booleans, and strings). If structured observations are supported, compare whole values, not projections of separate fields.

Retain all reachable possibilities. Equal observations do not justify merging states; hidden cycles can be closed only using the full model state and the matching progress (and any state needed to tell whether the history just completed, or any remaining bound). An original transition may have several possible source-site explanations; retain the eligible ones, rather than choosing an explanation from the state pair. Hidden reachability has no implicit transition bound in the required slice.

For every history compare **sets** of outcomes. Emit `+` for NEW-only outcomes and `−` for OLD-only outcomes only after the history is closed on both sides. A producing trace cannot prove the other side's absence. In a closed history with no matching execution, distinguish a label explicitly absent from a bound label that has no eligible successor after a reachable prefix and the permitted hidden steps. Do not diagnose a later label as blocked if its prefix was already unreachable. A recorded denial is a value from an executed path, not either of these cases.

## Evidence and status

- A witness for each reported addition/removal identifies the producing commit, scenario, history, outcome, original initialized state, and original transitions through the observation, including hidden steps. It supplies the original state values (or a lossless replay representation) and source-call provenance for public steps, so replay checks `init`, `step`, the label assignment, and the value. A valid native before/after edge alone does not distinguish two call sites with the same effect.
- In terminal and versioned structured JSON output, identify both commits, the scenario and bindings on each side, selected histories, hidden-step policy, observations, actual search scope, and completion status. Emit factual `+`/`−`, not a `Findings` column. Order histories by length first, then use a fixed tie/order rule for histories, deltas, and witness selection. A reproducible witness is required; finding the shortest original transition trace is not a separate release requirement. No LLMs or random simulation at any stage.
- `exhaustive` means all possibilities in the stated scenario, selected histories, and hidden-step policy were checked, not model equivalence. Optional explicit original-transition bounds are not required in this release. If offered, count original steps, including hidden steps but excluding initialization, and report `bounded` for coverage completed through that cutoff without a proof beyond it. No match through a cutoff is not proof a label is disabled without the cutoff.
- `incomplete` applies when the requested check cannot finish: unsupported scheduler or evaluation, bad snapshot or binding, unavailable backend, timeout, resource limit, interruption, or any unfinished outcome search. Identify the unresolved scope and cause (including the side where known). Do not display unresolved outcomes as an empty set or claim no change. A report may withhold all deltas, or include only histories closed on both sides and mark their completed scope separately. No manufactured delta from a partial result.

## What to carry forward

Carry the [experiment record](design-spiral.md), exact fixtures and upstream revisions, and the independent evidence into a fresh implementation. If it tracks labels in extra state, test on an **unfiltered** scheduler that erasing that state preserves the original initial states and the outgoing projected edges from each reachable tracked state. A global edge union can miss suppression in one tracking state; erasure alone cannot identify a wrong label, so check identity independently as well. Run these checks as regressions, not as a full-graph pass for every review. Witness replay checks presence; absence needs a separate closure check.

Do not inherit the experiment wrappers, compiler workarounds, binding syntax, flags, or JSON by default. Defer index and working-tree comparison, implicit histories, automatic cross-revision matching, arbitrary scheduler forms, and DML's locally bound argument mapping. Use the source-binding and imported consensus positives and the DML fail-closed case to test the first slice before expanding it.
